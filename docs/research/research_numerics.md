# digest
VERIFIED 2026-08-17. GHC baseline: 9.14.1 released 2025-12-19 is the first designated LTS (bugfix support to ≥ early 2028); 9.12.4 released 2026-03-27; active branches master/10.0/9.14/9.12/9.10, with 9.12+9.10 to be discontinued (GHC 10.0 = formerly 9.16). Stackage floor lags: LTS 24.53 = ghc-9.10.3 (2026-08-04); Nightly 2026-08-16 = ghc-9.12.4. No LTS on 9.12/9.14 yet. base map: 9.10→4.20, 9.12→4.21, 9.14→4.22, 10.0→4.23.

SIMD: GHC 9.12 added SIMD to the x86 NCG (128-bit only, most FP + few integer ops), plus vector FMA (fmaddFloatX4#), shuffles (shuffleFloatX4#), min/max primops. 9.14 extended NCG SIMD with 128-bit *integer* ops and dropped the -mavx requirement for shuffleFloatX4#/shuffleDoubleX2#. GHC 10.0 adds bitwise SIMD primops (ghc-prim 0.14: andDoubleX4#, orWord32X4#, xorInt8X16#) and -mavx512bw/dq/vl, -mgfni flags with implication hierarchy. AArch64 NEON only via LLVM (since 9.8). CRITICAL GAP: no library surfaces any of it — vector issue #251 closed unimplemented, `primitive` has no SIMD, primitive-simd/simd/vector-simd are pre-2020. Windows ABI needs 128-bit vectors passed by reference under UnliftedFFITypes. SSE2 assumed by default since GHC 8.10.

-fllvm: GHC docs state it "generally produces code with performance as good as the native code generator but for some cases can produce much faster code. This is especially true for numeric, array heavy code using packages like vector"; requires opt/llc on PATH, LLVM 13–21, "significant increase in compilation times". LinearTypes is still explicitly experimental with "really unreliable" multiplicity polymorphism — not a design foundation.

BLAS/LAPACK: hmatrix is de-facto but frozen — last Hackage release 0.20.2 on 2021-03-08, one metadata revision 2023-01-09, last master commit 2024-02-21. It still ships in LTS 24.53 and nightly, so it does build on 9.10/9.12. base bound is open (>=4.8 && <5). Windows stanza only sets extra-libraries (openblas | blas lapack); INSTALL.md self-declares "Some of these instructions are now very out of date"; Windows issues #236 (2017) and #284 (2018) remain open. Alternative: Thielemann's lapack-0.5.2 / lapack-ffi / blas-ffi-0.1 (2018) / comfort-array-0.5.5 — shape-typed but the FFI floor is 8 years stale. Windows is actually tractable in 2026: GHC ≥9.4.1 ships CLANG64 MSYS2, so the package is mingw-w64-clang-x86_64-openblas 0.3.34-1 (updated 2026-08-18) supplying libopenblas.dll/.a/.dll.a plus lapack.h/lapacke.h/cblas.h; GHCup's bootstrap already injects extra-include-dirs/extra-lib-dirs.

Ecosystem context: DataHaskell published Roadmap v1.0 (dated "November 2026") naming dataframe + Hasktorch + distributed-process as its three pillars, targeting Python-parity by Q4 2027. dataframe 3.5.0.0 (2026-08-14, mchav) is very active, built on `vector` columns (not massiv), and already ships PCA/KMeans/SVM/GBM/DBSCAN/GMM/logistic+linear regression/decision trees/metrics/plotting. Its author's benchmark (2025-07-17) claims Polars parity and ~2× Pandas (groupBy 119 ms vs 227 ms vs 376 ms). Hasktorch has no Windows support; accelerate's GPU backend "probably doesn't work on Windows".

# key_insights
- Q1 ANSWER — there is no single right substrate; the correct 2026 choice is layered: `vector` (Storable/Unboxed) as the buffer and interop currency, an orthotope/ox-arrays-style stride+LMAD view layer for n-D shape semantics, and C kernels for hot loops — because `vector` is the only piece with multiple maintainers and universal adoption (hmatrix, massiv, orthotope, ox-arrays, statistics, dataframe all depend on it).
- massiv is the most complete n-D array library and the best API to imitate, but adopting it as the core means inheriting a single-maintainer dependency that has had no release since 2025-05-31, no commit since 2025-07-08, a tested-with ceiling of GHC 9.12.1, and an open maintainer-filed issue (#146) blocking the 1.1.0.0 release.
- Q2 ANSWER — the BLAS/LAPACK situation is the ecosystem's weakest link: hmatrix has had no release in 5.4 years (0.20.2, 2021-03-08) and no commit in 2.5 years, its Windows instructions self-describe as "very out of date", and its Windows issues from 2017 and 2018 are still open; the Thielemann alternative is better-typed but rests on blas-ffi 0.1 from 2018.
- Windows BLAS is actually SOLVED at the system level and only broken at the Haskell packaging level: GHC ≥9.4.1 ships a CLANG64 MSYS2 environment, GHCup's bootstrap already injects extra-include-dirs/extra-lib-dirs, and mingw-w64-clang-x86_64-openblas 0.3.34-1 (updated 2026-08-18) provides libopenblas.dll/.a/.dll.a plus cblas.h/lapack.h/lapacke.h — so binding cblas/lapacke directly (not Fortran symbols, not hmatrix's build system) makes Windows a first-class target.
- Q3 ANSWER — GHC now has real 128-bit SIMD in the x86 native code generator (FP in 9.12, integers in 9.14, bitwise in 10.0, plus FMA/shuffle/minmax primops and AVX-512 feature flags in 10.0), but ZERO libraries expose it: vector's SIMD issue was closed unimplemented, `primitive` has none, and primitive-simd/simd/vector-simd are all pre-2020 — this is an open, high-value niche a new toolkit could claim.
- The pragmatic performance path in 2026 is not GHC SIMD and not -fllvm but hand-written C kernels compiled with -O3/-march=native, which is exactly what ox-arrays does (cbits/arith.c, `nonportable-simd` flag) — and horde-ad, the most carefully tuned numeric package in the ecosystem, uses -fspecialise-aggressively/-fexpose-overloaded-unfoldings/-fpolymorphic-specialisation rather than -fllvm.
- LinearTypes must not appear in the public API: GHC 9.14 still calls the extension experimental with "everything down to the syntax is subject to change" and multiplicity polymorphism "really unreliable", so in-place-mutation-by-linearity is a research bet, not an engineering foundation.
- Target GHC 9.10 as the floor and 9.14 as the forward target: 9.14.1 (2025-12-19) is GHC's first LTS with support to ~2028, but Stackage's newest LTS 24.53 is still ghc-9.10.3 and nightly is only ghc-9.12.4, so a 9.14-only project would have no snapshot to build against.
- horde-ad is the only surveyed numeric package whose cabal declares tested-with GHC 9.14.1, making the orthotope→ox-arrays→horde-ad line the most GHC-current numeric stack in Haskell — and the clearest existing blueprint for AD-over-tensors architecture, despite self-describing as an "early prototype".
- Competitive reality check: DataHaskell published Roadmap v1.0 naming dataframe + Hasktorch + distributed-process as its pillars with Python-parity targeted for Q4 2027, and `dataframe` 3.5.0.0 (uploaded 2026-08-14, three days ago) already ships PCA, KMeans, SVM, GBM, AdaBoost, DBSCAN, GMM, decision trees, logistic/linear regression, metrics and plotting on `vector` columns — a new toolkit must either interoperate with it or explain why it is duplicating a very active effort.
- Windows-first is a genuine, defensible differentiator: hasktorch's README lists only Linux/macOS, accelerate's GPU backend "probably doesn't work on Windows", hmatrix's Windows path is bit-rotted, and dataframe documents no Windows story — a DS toolkit that installs and runs on Windows with zero system dependencies would be unique in the ecosystem.
- Accelerate's 2026 revival is real and changes the GPU calculus — 1.4.0.0 (2026-04-02, first release since 2020) plus accelerate-llvm-native's "Support for LLVM-15 to 22" and system-linker use finally broke the llvm-hs version lock that killed it — but it is a deeply embedded EDSL, so it can only ever be an optional backend behind a stable front-end, never the substrate for a numpy-shaped API.
- The bus-factor map should drive dependency choices: vector = 3 maintainers (safe), linear/ad = Kmett+Scott+Mertens (safe), orthotope/ox-arrays/horde-ad = Konarski+Smeding (2, active), accelerate = newly reinforced (Smeding/ivogabe/Tjalle-S), massiv = 1 and slowing, dataframe = 1 but very fast, hmatrix = effectively 0, repa = compat-only, sparse-linear-algebra (2018) and dense-linear-algebra (2018) = dead.
- orthotope's README explicitly disclaims kernels — "For more algorithmic operations, e.g., matrix multiplication, we suggest using a different library, like hmatrix" — which means the ecosystem currently has NO library that combines a good stride/view model with good numerical kernels; that gap is precisely the space a new toolkit should occupy.
- statistics 0.16.5.0 (2026-01-09) still depends on the pure-Haskell dense-linear-algebra 0.1.0.0 (2018) rather than hmatrix, which is direct evidence that the ecosystem's most-used statistics package deliberately refuses a BLAS dependency for installability — a new toolkit should offer a pure-Haskell fallback path alongside the accelerated one.

## vector (1-D Int-indexed immutable/mutable arrays (Boxed/Unboxed/Storable/Primitive) with stream fusion; the universal storage/interchange floor of the Haskell ecosystem)
STATUS: HEALTHY / actively developed. Latest Hackage release 0.13.2.0, "Uploaded by AlexeyKhudyakov at 2024-10-31T18:01:59Z". master is alive: latest commit 2026-06-23 (PR #561). Maintainers: Alexey Kuleshevich, Aleksey Khudyakov, Andrew Lelechenko. base >=4.9 && <4.23 → covers GHC 8.0–9.14 (base 4.22). Unreleased NEXT_VERSION adds traverse & friends, mapInPlace/imapInPlace(M), UnboxViaStorable, iconcatMap.
ASSESS: STRENGTHS: universal — hmatrix, massiv, orthotope, ox-arrays, statistics, dataframe all depend on it, so it is the zero-cost interop currency; Storable variant is directly FFI/BLAS-compatible (Ptr + length); stream fusion is mature; multiple maintainers = low bus factor; long release gap is stagnation of API surface, not of maintenance. WEAKNESSES: 1-D only (no shape/stride/rank), no parallelism, no SIMD (issue #251 closed with no implementation, no SIMD entry in any changelog), fusion is fragile across module boundaries and defeated by non-inlined polymorphism. FIT: the correct *buffer* layer for a new DS stack — build the n-D strided view layer above `Data.Vector.Storable`, never re-invent the buffer.
EVID: https://hackage.haskell.org/package/vector ; https://github.com/haskell/vector/commits/master ; https://github.com/haskell/vector/blob/master/vector/changelog.md ; https://github.com/haskell/vector/issues/251

## massiv (Multi-dimensional arrays with delayed-representation fusion, stencils, and parallel computation via the `scheduler` package)
STATUS: SLOWING / one-maintainer risk. Latest 1.0.5.0, "Uploaded by lehins at 2025-05-31T17:37:58Z". Last master commit 2025-07-08. tested-with tops out at GHC ==9.12.1; base >=4.9 && <5 (no upper-bound blocker for 9.14). Present in Stackage nightly 2026-08-16 (ghc-9.12.4) and LTS 24.53. Open issue #146 "Needed maintenance before massiv-1.1.0.0 release" (2025-05-25, filed by the maintainer himself) still open; newest open issue #156 dated 2026-06-09. Single maintainer: lehins.
ASSESS: STRENGTHS: by far the most complete n-D array API in Haskell — manifest vs delayed representations, real fusion, stencil DSL with bounds handling, genuinely usable parallelism (not just +RTS -N magic), good docs, `unsafe-checks` flag for a debug build. It is the only library that already covers the numpy-shaped surface area. WEAKNESSES: bus factor 1 and visibly decelerating (14 months since last release, 13 months since last commit as of today); no SIMD; no BLAS/LAPACK; no GPU; no verified GHC 9.14 story; Windows is untested in CI/README. FIT: the strongest single candidate to build on, and the best API to copy, but adopting it means inheriting a single-maintainer dependency for the toolkit's core. A serious project should either co-maintain it or vendor its ideas.
EVID: https://hackage.haskell.org/package/massiv ; https://hackage.haskell.org/package/massiv-1.0.5.0/massiv.cabal ; https://github.com/lehins/massiv/commits/master ; https://github.com/lehins/massiv/issues ; https://www.stackage.org/nightly/package/massiv

## hmatrix (Dense linear algebra: solvers, decompositions, eigen/SVD, backed by BLAS + LAPACK; plus Numeric.LinearAlgebra.Static for dimension-checked matrices)
STATUS: FROZEN. Latest 0.20.2, "Uploaded by DominicSteinitz at 2021-03-08T08:41:57Z" — 5.4 years without a release. Only one metadata revision (rev:1, 2023-01-09, Bodigrim, bumping the `split` bound). Last GitHub commit on master 2024-02-21. Long-open Windows issues #236 (opened 2017-08-31) and #284 (opened 2018-10-16).

## accelerate (Embedded (deeply-embedded EDSL) language for high-performance array computation, JIT-compiled to multicore CPU via LLVM and to NVIDIA GPUs via PTX)
STATUS: REVIVED and ACTIVE. accelerate 1.4.0.0, "Uploaded by tomsmeding at 2026-04-02T16:43:06Z" (changelog dated 2026-03-30); previous release 1.3.0.0 was 2020. Last master commit 2026-06-20 (ivogabe). ASSESS: STRENGTHS: the only credible GPU path in Haskell; the 2026 revival is real (two releases + ongoing commits after a 6-year gap); LLVM 15–22 support and system-linker use fixed the historic llvm-hs version-lock that killed it; README now documents a native Windows install (WinGet/LLVM installer + VS Build Tools). FIT: an optional acceleration *backend* behind a stable front-end API, never the core.

## orthotope (APL-inspired multidimensional arrays with stride/LMAD representation; Dynamic/Ranked/Shaped type-safety tiers over generic/storable/unboxed vector backends)
STATUS: ACTIVE (narrow scope). Latest 0.1.8.0, "Uploaded by MikolajKonarski at 2026-02-16T21:33:02Z"; last commit 2026-02-16. Maintainers Lennart Augustsson + Mikolaj Konarski. base >=4.12 && <4.23, vector >=0.12 && <0.14.
ASSESS: STRENGTHS: the cleanest *representation* in the ecosystem — stride vectors mean transpose/replicate/broadcast are metadata-only, which is exactly the numpy view semantics a DS toolkit needs; three type-safety tiers let a library expose both dynamic and statically-shaped APIs from one core; currently maintained and GHC-current. WEAKNESSES: deliberately scope-limited — the README states its API is "mostly structural operations" and explicitly says "For more algorithmic operations, e.g., matrix multiplication, we suggest using a different library, like hmatrix." No kernels, no parallelism, no BLAS, no SIMD. FIT: the right *shape/stride/view* model to adopt or copy for the toolkit's tensor type; must be paired with a separate kernel layer.
EVID: https://hackage.haskell.org/package/orthotope ; https://github.com/augustss/orthotope/commits/master

## ox-arrays (CPU tensor library layering nested struct-of-arrays (Ranked/Shaped/Mixed) on orthotope's strided representation, with hand-written C arithmetic kernels)
STATUS: ACTIVE, NEW. Latest 0.2.0.1, "Uploaded by MikolajKonarski at 2026-04-23T08:13:58Z"; upstream repo git.tomsmeding.com/ox-arrays, last commit 2026-04-14. Maintainers Tom Smeding + Mikolaj Konarski. base >=4.18 && <4.23. Ships cbits/arith.c compiled with -O3 -std=c11, defaulting to -msse2 on x86_64/i386, with a `nonportable-simd` flag that adds -march=native.
ASSESS: STRENGTHS: the most modern design in the ecosystem — strided/LMAD views, struct-of-arrays via the Data.Vector.Unboxed data-family trick, sharing preservation, first-order ops chosen for vectorizability, and the pragmatic decision to put the hot loops in C rather than fight GHC's codegen. It is the only Haskell array library that actually gets SIMD today (via the C compiler, not GHC). WEAKNESSES: young (0.2.x), effectively a purpose-built backend for horde-ad rather than a general-purpose library; no BLAS/LAPACK; no parallelism story; hosted off GitHub which raises contribution friction; `-march=native` is a build-machine-specific hack, not a runtime dispatch. FIT: strong evidence for the architecture a new toolkit should adopt — Haskell for shape/type logic, C (or Rust/zig) for kernels. Consider depending on it, or replicating its cbits approach with runtime CPU dispatch.
EVID: https://hackage.haskell.org/package/ox-arrays ; https://hackage.haskell.org/package/ox-arrays-0.2.0.1/ox-arrays.cabal ; https://git.tomsmeding.com/ox-arrays

## horde-ad (Higher-order reverse-mode automatic differentiation over arrays, with symbolic derivative-program generation; targets FC/RNN/CNN/ResNet training)
STATUS: ACTIVE, most GHC-current numeric package found. Latest 0.3.0.0, "Uploaded by MikolajKonarski at 2026-04-14T19:42:35Z"; last commit 2026-08-12 (five days ago). tested-with: GHC ==9.10.3 || ==9.12.4 || ==9.14.1 — the only surveyed library verified against GHC 9.14. base >=4.20.1 && <4.23; builds on orthotope >=0.1.8 && <0.1.9 and ox-arrays >=0.2 && <0.3, vector >=0.13.2.
ASSESS: STRENGTHS: real, current, and correctly layered (AD logic separated from the tensor backend); README claims "Benchmarks suggest that horde-ad has competitive performance on CPU"; its cabal file is a masterclass in what actually makes numeric Haskell fast — -fspecialise-aggressively, -fexpose-overloaded-unfoldings, -fpolymorphic-specialisation, -fworker-wrapper-cbv, -fdicts-cheap, -flate-dmd-anal, -fkeep-auto-rules (notably NOT -fllvm). WEAKNESSES: self-described "early prototype, both in terms of the engine performance, the API" that "will fail on cases not found in current tests"; efficiency is "confined to a narrowly typed class of source programs with limited higher-orderness"; no accelerator backend yet; 41 open issues. FIT: the reference implementation for the toolkit's autodiff layer, and the single best source of GHC optimization-flag guidance. Too immature to depend on for a v1 public API.
EVID: https://hackage.haskell.org/package/horde-ad ; https://hackage.haskell.org/package/horde-ad-0.3.0.0/horde-ad.cabal ; https://github.com/Mikolaj/horde-ad ; https://github.com/Mikolaj/horde-ad/commits/master

## ad (Kmett) (Forward-, reverse- and mixed-mode automatic differentiation combinators with type-level branding of infinitesimals (Forward/Reverse/Kahn/Sparse/Tower))
STATUS: MAINTAINED but quiet. Latest 4.5.6, "Uploaded by ryanglscott at 2024-05-01T12:25:29Z". Maintainers Edward Kmett, Eric Mertens, Ryan Scott.
ASSESS: STRENGTHS: the type-level branding trick that prevents perturbation confusion is correct and elegant; broad API (grad, jacobian, hessian, directional derivatives, higher-order); maintained by a reliable trio (Ryan Scott is a prolific ecosystem maintainer). WEAKNESSES: scalar/Traversable-oriented, not array-oriented — it differentiates `f :: forall s. FIT: correct choice for scalar optimization/statistics (MLE, optimizers), wrong choice as the ML autodiff engine. A DS toolkit likely needs both `ad` for scalar work and a horde-ad-style array AD for models.
EVID: https://hackage.haskell.org/package/ad

## lapack / lapack-ffi / blas-ffi / comfort-array (Thielemann stack) (Alternative BLAS+LAPACK route: autogenerated low-level Fortran FFI (blas-ffi, lapack-ffi) under a high-level shape-typed API (lapack) built on comfort-array's shape-indexed arrays)
STATUS: MIXED. lapack 0.5.2, "Uploaded by HenningThielemann at 2024-05-18T17:19:01Z"; comfort-array 0.5.5, same day. But the FFI floor is old: blas-ffi 0.1, "Uploaded by HenningThielemann at 2018-12-20T09:26:27Z". Single maintainer across the whole stack.
ASSESS: STRENGTHS: the shape-type system (Range, Shifted, ZeroBased, Cyclic, Enumeration, Triangular, Simplex) is more expressive than hmatrix's Static and encodes banded/triangular/Hermitian structure at the type level — the right idea for a typed DS library; covers Float/Double/Complex uniformly; more recently released than hmatrix. WEAKNESSES: bus factor 1; low adoption compared to hmatrix so the community knowledge base is thin; blas-ffi documents having removed SCABS1/DCABS1 bindings because they are "missing in some optimized alternative implementations like OpenBLAS and ATLAS" — a concrete symptom of the reference-BLAS-vs-OpenBLAS symbol drift a new binding must handle; no documented Windows story. FIT: the best existing *design* reference for typed linear algebra; a new toolkit should probably bind cblas/lapacke (C interfaces, which OpenBLAS ships headers for) rather than raw Fortran symbols, avoiding both stacks' name-mangling fragility.
EVID: https://hackage.haskell.org/package/lapack ; https://hackage.haskell.org/package/blas-ffi ; https://hackage.haskell.org/package/comfort-array

## dataframe (DataHaskell) (pandas/Polars-style DataFrame with untyped/typed/monadic API layers, CSV+Parquet+JSON I/O, plus a surprisingly complete classical-ML module set)
STATUS: VERY ACTIVE — the fastest-moving package in the space. Latest 3.5.0.0, "Uploaded by mchav at 2026-08-14T06:18:04Z" (three days ago). tested-with GHC ==9.4.8 || ==9.6.7 || ==9.8.4 || ==9.10.3 || ==9.12.2. Built on vector >=0.13 && <0.15 columns — explicitly NOT massiv. Exposes DataFrame.DecisionTree, LinearModel.Regression/Logistic, SVM, KMeans, PCA, DBSCAN, GMM, Boosting.GBM, Boosting.AdaBoost, Metrics, and Display.Web.Plot/Chart + Display.Terminal.Plot. Sub-packages dataframe-core/-csv/-parquet/-persistent. Named pillar #1 in DataHaskell Roadmap v1.0.
ASSESS: STRENGTHS: it already occupies the pandas niche and is encroaching on the scikit-learn niche; author-run benchmarks (2025-07-17, HP Dragonfly G4 / 32 GB) show Haskell 15.26 s at 300M elements where Polars and Pandas OOM'd, and groupBy 119 ms vs Polars 227 ms vs Pandas 376 ms; columnar layout with bitmap-backed nullability is the right modern design; three API tiers mirror the exploration→production path. WEAKNESSES: bus factor 1 (mchav); no massiv/BLAS integration — its numerics are hand-rolled over vector, which will cap linear-algebra-heavy ML; not tested past GHC 9.12.2; Windows support undocumented. FIT: CRITICAL COMPETITIVE INTELLIGENCE — a new DS toolkit either integrates with dataframe (share the vector-columnar representation) or duplicates a year of very active work. This is the strongest argument for choosing `vector` as the interchange substrate.

## arrayfire (Haskell bindings to the ArrayFire general-purpose GPU library (CUDA/OpenCL/CPU backends) covering BLAS, LAPACK, signal processing, image processing, statistics, sparse arrays)
STATUS: ALIVE, quietly. Latest 0.9.0.0, "Uploaded by DavidJohnson at 2026-06-13T20:14:37Z". Single maintainer, David Johnson (code@dmj.io).
ASSESS: STRENGTHS: the widest feature surface of any GPU option (BLAS + LAPACK + FFT + image + vision + sparse in one library), backend-swappable at runtime (CUDA/OpenCL/CPU), and released as recently as June 2026 — much healthier than its reputation. ArrayFire itself has real Windows binaries, unlike libtorch-via-hasktorch in Haskell. WEAKNESSES: bus factor 1; requires the user to install the ArrayFire runtime; upstream ArrayFire's own momentum is questionable; the Haskell layer is thin bindings, so no idiomatic/typed API; little visible community usage. FIT: an underrated fallback GPU/accelerated backend, and the only one with a plausible Windows GPU story. Worth a spike before defaulting to accelerate.
EVID: https://hackage.haskell.org/package/arrayfire

## GHC itself (SIMD primops, -fllvm, unboxed types, LinearTypes) (The compiler substrate: vector primops, backends, and type-system features relevant to numerics)
STATUS: 9.14.1 released 2025-12-19 = first designated LTS (support ≥ early 2028); 9.12.4 released 2026-03-27; branches master/10.0/9.14/9.12/9.10 with 9.12+9.10 slated for discontinuation; GHC 10.0 is the renamed 9.16. Stackage LTS 24.53 = ghc-9.10.3 (2026-08-04); Nightly 2026-08-16 = ghc-9.12.4 — no LTS snapshot on 9.12 or 9.14 yet.
ASSESS: SIMD: 9.12 brought SIMD into the x86 NCG (128-bit only, most FP ops, few integer ops) plus vector FMA (fmaddFloatX4#/fnmsubDoubleX2#), shuffles (shuffleFloatX4#), and min/max. 9.14: "SIMD support in the x86 native code generator has been extended with 128-bit integer operations. Also, shuffleFloatX4# and shuffleDoubleX2# no longer require -mavx." GHC 10.0: bitwise SIMD primops (ghc-prim 0.14: andDoubleX4#, orWord32X4#, xorInt8X16#) plus -mavx512bw/-mavx512dq/-mavx512vl/-mgfni and an implication hierarchy (-mavx implies -msse4.2; -mavx512f implies -mfma and -mavx2). AArch64 NEON only via LLVM (9.8+). SSE2 assumed by default since 8.10. THE GAP: zero library exposure — vector #251 closed unimplemented, `primitive` 0.9.1.0 (2025-03-31) has no SIMD, and primitive-simd/simd/vector-simd are abandoned; Windows requires 128-bit vectors passed by reference under UnliftedFFITypes; no SIMD in the WASM/RISC-V/JS/via-C backends. -fllvm: GHC docs say it "generally produces code with performance as good as the native code generator but for some cases can produce much faster code. This is especially true for numeric, array heavy code using packages like vector" — but it needs opt/llc on PATH, LLVM 13–21, and causes "a significant increase in compilation times"; horde-ad, the most performance-tuned numeric package in the ecosystem, notably does NOT use it. LinearTypes: "currently considered experimental, expect bugs, warts, and bad error messages; everything down to the syntax is subject to change"; multiplicity polymorphism is "incomplete and experimental... really unreliable" with no multiplicity multiplication, no linear pattern synonyms/@-patterns/view patterns, and TH "will probably not work" — 9.14 only added non-linear record fields. FIT: target GHC 9.10 (Stackage LTS floor) with 9.14 (GHC LTS) as the forward target; rely on unboxed/Storable + ByteArray# and aggressive specialisation flags for speed; treat GHC SIMD as a research track (or an opportunity to ship the missing wrapper library) and LinearTypes as off-limits for public API design.
