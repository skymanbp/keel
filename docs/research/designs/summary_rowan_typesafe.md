# Rowan — proofs over plans (repo: HSDS)

## philosophy
THESIS: The only durable reason to do data science in Haskell is the class of errors Python cannot rule out. So the product is the type system — but shipped as an ERASABLE PROOF LAYER, never as the runtime representation. Types describe the plan; they are not the plan.

Three commitments, in priority order:

1. TYPED FACADE OVER A DYNAMIC CORE (the deliberate layering choice the brief demands). Rowan does not build a DataFrame runtime. `Frame (s :: Schema)` is a newtype over `dataframe-core`'s existential-GADT `DataFrame` (dataframe-core 2.4.0.0, 2026-08-14: modules DataFrame.Core, DataFrame.Typed.Schema, ...; deps only base/containers/primitive/random/text/vector — verified on Hackage). Five reasons this direction and not the reverse:
   (a) ERASURE IS TOTAL, RECONSTRUCTION IS PARTIAL. `erase :: Frame s -> DataFrame` is `coerce`. Going the other way needs runtime validation, so it can only live at the IO boundary. Put the cheap direction inward.
   (b) THE RUNTIME ALREADY EXISTS AND IS ALIVE. Rebuilding columnar storage + bitmap nullability + CSV/Parquet + a lazy executor duplicates ~1,267 commits and repeats javelin's fate (competent, lost, 19 downloads/30d).
   (c) OPTIMIZER VISIBILITY (Spark's `Dataset[T]` lesson). Catalyst cannot see through typed lambdas, so Spark's typed API lost to the untyped one. Rowan's `Expr s a` is a GADT of REIFIED OP CODES that erases to dataframe's untyped `Expr` AST — the optimizer sees exactly what it saw before. Types are on the outside; no closure is ever hidden inside the plan.
   (d) GHC-VERSION RESILIENCE. Frames died because its typed representation WAS its runtime (vinyl rows + mandatory TH + pipes), so every GHC bump was a rescue project; last release and last commit are both 2023-10-22, GHC ≤9.4.6. A newtype+phantom layer is nearly free to port.
   (e) DELETABILITY. Every Rowan program has a mechanical de-typing: drop the schema, call the dataframe function. Users can bail out mid-pipeline. Frames had no exit.

2. FRAMES' USABILITY FAILURE IS AN ENGINEERING BUG, AND IT GETS A CI GATE. mchav's design doc is right that type-level programming "doesn't make for intuitive APIs" — about type-level REPRESENTATION. It is not an argument against type-level PROOF. The counter-evidence has to be mechanical, so: a golden-type-error corpus is a first-class deliverable from milestone 1. ~60 known-bad programs are compiled in CI and their GHC output byte-compared to checked-in `.golden` files. A change that makes an error longer or less specific fails the build. Every partial type family and every row-algebra class gets a HUMAN-WRITTEN message via `GHC.TypeError.Unsatisfiable` (GHC proposal #433, added in base-4.19.0.0 / GHC 9.8, so available at our GHC 9.10 floor). Companion gate: a "no-annotation" suite where every canonical usage must typecheck with zero type applications and zero signatures.

3. HARD CEILING ON MACHINERY. GHC2021 + DataKinds/TypeFamilies/GADTs/FunctionalDependencies, and nothing above it. No `singletons-base` (3.5.1, 2026-01-11: pinned to GHC 9.14.1 exactly, "all reported builds failed" on Hackage, 18 downloads/30d — a dependency that pins one GHC is fatal). No LinearTypes (GHC 9.14 still: "everything down to the syntax is subject to change"). No RequiredTypeArguments in public API (erased; no dependent pattern matching, so runtime shape checks are mandatory anyway). No Template Haskell on the required path — `rowan-th` exists and is always optional, because requiring TH is the single most-cited reason Frames feels like "an advanced Haskell tool rather than a data science tool".

What this buys that Python structurally cannot: schema flow checked across a whole pipeline; fit-before-transform and train-vs-test leakage as TYPE errors, not convention; units-of-measure on columns at zero runtime cost; shape-checked tensor ops; hyperparameters as inspectable data for free via Generic.

## scope
IN v1 (0.1, milestones M0–M7 — a complete product with no tensors, no AD, no GPU, no PPL):

- `rowan-schema`: the schema protocol. Type-level `Schema = [Field]` where `Field` carries name (Symbol), element type, and nullability. Row algebra as closed type families + fundep classes: Lookup / Select / Insert / Drop / Rename / Disjoint / Union / JoinSchema. Generic-derived `SchemaOf r` for user records. Every failure mode has a hand-written `Unsatisfiable` message. Deps: base + barbies only. Shipped FIRST and ALONE (the Tables.jl lesson: publish the protocol before any implementation so competing implementations cannot fork the ecosystem).
- `rowan-frame`: `Frame (s :: Schema)` over dataframe-core's `DataFrame`; `erase`/`checkSchema`; HKD bridge to/from user record types (closes the "two independent type systems" seam flagged on Discourse).
- `rowan-expr`: `Expr s a` GADT of reified op codes, `OverloadedLabels` columns (`#age :: Expr s Int`), erasing to dataframe's untyped expression AST. Typed select/filter/withColumn/groupBy/agg/join/window.
- `rowan-io`: `readCsvAs @Schema` / `readParquetAs @Schema` with column-level structured `SchemaError` diffs (directly answers dataframe issue #177, silent Double→Int inference); Arrow C Data Interface INBOUND import (an unfilled ecosystem gap — dataframe-arrow is export-only, harrow/hs-arrow are dead at 1 and 6 commits).
- `rowan-pipeline`: the flagship. `Estimator`/`Transformer` contract, `Pipeline (p :: Phase) sIn sOut` as a free category (inspectable, not a closure chain), Phase-indexed fit/transform, Role-indexed train/test splits, hyperparameters-as-data via Generic, `crossValidate`, `gridSearch`.
- `rowan-learn`: typed wrappers over dataframe-learn 2.4.1.0's existing estimators (linear/ridge/lasso/elastic-net, logistic, SVM, trees, GBM, AdaBoost, PCA, kPCA, k-means, GMM, DBSCAN) + metrics. Wrapping, NOT reimplementing — that library already asserts scikit-learn parity in its own test suite (Learn.SklearnParity).
- `rowan-viz`: typed grammar of graphics; encodings checked against the frame's schema; backends = Vega-Lite JSON spec, `chart-svg` (static, zero C deps), terminal.
- `rowan-shape`: type-level Nat/shape vocabulary + units-of-measure integration via `dimensional` 1.6.2.
- `rowan`: umbrella + `Rowan.Prelude` + docs + measured time-to-first-plot on a clean Windows box.

IN v1.x (M8–M9, only after 0.1 ships):
- `rowan-tensor` (strided LMAD views, Dynamic/Ranked/Shaped tiers, C kernels with RUNTIME cpu dispatch, pure-Haskell fallback), `rowan-tensor-blas` (flag-gated cblas/lapacke), `rowan-stats` (units-aware wrappers over `statistics`), `rowan-prob` (probability monad).

EXPLICITLY OUT, permanently or until someone else pays for it:
- A new DataFrame runtime, CSV reader, Parquet codec, or streaming/query executor. All four exist in dataframe-*; duplicating them is how this project would die.
- Deep learning / autodiff engine. HLearn's author paused development, said "Haskell has poor support for numerical computing", rewrote the numeric prelude (SubHask), then blocked on dependent types estimating a 5–10 year wait. We do not write an AD engine. `rowan-torch` may later wrap hasktorch (no Windows) behind the same Estimator contract.
- GPU. accelerate is an EDSL (wrong substrate for a numpy-shaped API) and its GPU backend "probably doesn't work on Windows".
- Any dependency on hmatrix (frozen at 0.20.2, 2021-03-08; Windows issues #236/#284 open since 2017/2018), Frames/vinyl, pipes, Chart-cairo, singletons, or hs-onnxruntime-capi (AGPL-3.0-only).
- Chasing "data scientists tired of Python". That segment is a mirage — mchav found DS outsiders "a little hard to get to complete" even a survey. The verified buyer is the Haskell developer with an occasional data task (14.53% of State of Haskell 2025, n=1417, want ML content).
- Anything gated on a future GHC feature. Π/Σ types are unscheduled; the Dependent Haskell roadmap page (updated 2026-08-14) declines to give a timeline.

PLATFORM SCOPE: Windows is a first-class target with CI on windows-latest from day zero (nobody in this space has Windows CI — not hasktorch, not dataframe, not hmatrix). The DEFAULT install path has ZERO native dependencies. GHC floor 9.10.3 (Stackage LTS 24.55), primary 9.12.4 (Stackage nightly, full HLS 2.14 support, and the first version where -fllvm links floating-point code on Windows — GHC #22487 breaks it on ≤9.10, which is exactly what GHCup recommends), forward target 9.14.1 (the GHC LTS, only "basic" HLS support, no Stackage snapshot).

## critique (score 3)
### fatal
- THE CORE GAP DOES NOT EXIST — the typed layer Rowan proposes to build is ALREADY SHIPPED INSIDE ROWAN'S OWN HARD DEPENDENCIES. dataframe-core 2.4.0.0 (uploaded 2026-08-14T06:17:58Z, https://hackage.haskell.org/package/dataframe-core) exposes DataFrame.Typed.Schema, DataFrame.Typed.Types, DataFrame.Typed.Record, DataFrame.Typed.Generic, DataFrame.Typed.Freeze, DataFrame.Typed.Util. DataFrame.Typed.Schema already provides: schemas as type-level [(Symbol, Type)]; Lookup/SafeLookup/HasName; RemoveColumn, SetColumnType, SubsetSchema, ExcludeSchema, RenameInSchema/RenameManyInSchema, Append/Snoc/Reverse, ColumnNames; AssertAbsent, AssertPresent, AssertAllPresent, AssertDisjoint, AssertKeyTypesMatch, AssertAllColumnsHaveType, AssertRealColumn, AllColumnsReal, AllDouble; nullability via StripAllMaybe/StripMaybeAt/ToMaybe/WrapMaybe/WrapMaybeColumns; SharedNames/UniqueLeft/CollidingColumns and InnerJoinSchema/LeftJoinSchema/RightJoinSchema/FullOuterJoinSchema; GroupKeyColumns; and a KnownSchema class with schemaEvidence :: [(Text, SomeTypeRep)] for runtime reflection (https://hackage-content.haskell.org/package/dataframe-core-2.4.0.0/docs/DataFrame-Typed-Schema.html). That is rowan-schema (M1, weeks 2-5, 'THE PROTOCOL, shipped first and alone') and rowan-frame's Generic/HKD bridge, item for item. dataframe-operations 2.4.0.0 (2026-08-14T06:17:59Z) additionally exposes DataFrame.Typed.Expr (+ .Extra), .Access, .Aggregate, .Apply, .Join, .Operations, .Sampling, .Statistics; DataFrame.Typed.Expr already ships `TExpr cols a` ('A typed expression validated against schema cols'), `col @"salary"`, OverloadedLabels `#age`, the full comparison/arithmetic/exponentiation/logical operator families INCLUDING separate nullable-aware variants (.+. vs .+, .>. vs .>) that Rowan's Expr sketch does not have, plus sum/mean/median/count/minimum/maximum/collect and castExpr/castExprWithDefault/unsafeCastExpr (https://hackage-content.haskell.org/package/dataframe-operations-2.4.0.0/docs/DataFrame-Typed-Expr.html). Rowan's M1+M2 — ten weeks and its two foundational packages — is a reimplementation of shipped, maintained code in the two packages it depends on. The design document read a digest that flagged 'DataFrame.Typed with full compile-time schema tracking' and asserted the gap anyway.
- ROWAN'S SCHEMA KIND IS GRATUITOUSLY INCOMPATIBLE WITH THE ONE ITS RUNTIME USES, SO IT IS A COMPETING TYPED API, NOT A FACADE. dataframe encodes Schema = [(Symbol, Type)] with nullability as Maybe in the element type (WrapMaybe/StripMaybeAt). Rowan encodes Schema = [Field], Field = 'Fld Symbol Type Nullability with a separate Nullability kind. These do not unify. Consequence: `erase` gets a Rowan user only to the UNTYPED DataFrame; every one of dataframe-operations' eight DataFrame.Typed.* modules (Typed.Join, Typed.Aggregate, Typed.Sampling, Typed.Statistics, ...) is unreachable from a `Frame s` without a translation shim Rowan must write and maintain against a dependency that shipped 1.0.0.0 on 2026-03-22 and 3.5.0.0 on 2026-08-14. Two typed layers with different schema kinds inside one dependency cone is the javelin fragmentation outcome the design explicitly says it is avoiding — except worse, because the competitor is also the upstream whose goodwill the collaboration posture depends on.
- THE CENTRAL ARCHITECTURAL RULE BUYS NOTHING: THE ERASURE TARGET ALREADY CONTAINS CLOSURES. The design calls 'Expr contains no `a -> b`' 'the single most important architectural rule in the project' and 'the direct application of the Spark Dataset failure'. But dataframe-core's untyped AST, DataFrame.Internal.Expression, is: `data Expr a where Col :: Columnable a => Text -> Expr a; Lit :: ...; Unary :: (UnaryOp op, ...) => op b a -> Expr b -> Expr a; Binary :: (BinaryOp op, ...) => op c b a -> Expr c -> Expr b -> Expr a; If; Agg; Over; CastWith :: ... -> (Either String a1 -> a) -> Expr a`, where the op arguments are `UnUDF a b = MkUnaryOp { unaryFn :: a -> b, unaryName :: Text, unarySymbol :: Maybe Text }` and `BinUDF a b c = MkBinaryOp { binaryFn :: a -> b -> c, binaryName, binarySymbol, binaryCommutative :: Bool, binaryPrecedence :: Int }` (https://hackage-content.haskell.org/package/dataframe-core-2.4.0.0/docs/DataFrame-Internal-Expression.html). Every arithmetic node in the target AST IS a closure carrying metadata. `eraseExpr :: Expr s a -> D.Expr` must therefore produce closure-carrying nodes, and the downstream optimizer (DataFrame.Internal.Simplify, dataframe-lazy) sees exactly the same name/symbol/commutativity/precedence metadata it sees for an untyped user. Rowan's reified PrimOp GADT adds zero optimizer visibility. The headline justification (c) for the whole layering is vacuous.
- 'THE LAYER NOBODY OWNS' IS ALSO ALREADY OWNED. rowan-pipeline is billed as 'THE DIFFERENTIATOR, and the piece the ecosystem provably lacks'. dataframe-learn 2.4.1.0 (2026-08-14, https://hackage.haskell.org/package/dataframe-learn) ships DataFrame.ModelSelection with `crossValidate` (k-fold) and `gridSearch`, plus pipelines that 'compose as a monoid' via <> and 'can be compiled into single expressions'. Note the second clause: mchav's pipelines COMPILE INTO THE EXPRESSION AST, whereas Rowan's L4 explicitly keeps estimator internals as closures (`stepFit :: params -> Frame sIn -> IO model`, `stepApply :: model -> Frame sIn -> Frame sOut`) behind a free category whose only inspectable content is names and params. On the design's own Spark criterion, the incumbent's pipeline is MORE optimizer-visible than Rowan's. The genuine delta reduces to the Phase index, the Role index, and Generic hyperparameter introspection — roughly one module, not a 13-package project.
- THE UNITS-OF-MEASURE CLAIM IS FALSE AS STATED, AND IT BREAKS THE WORKED EXAMPLE. The design asserts twice that `Quantity d a` columns are 'coerce-identical to its underlying Double vector' and cost 'exactly zero bytes and zero cycles'. dataframe-core's element universe decides boxing by a CLOSED type family with a catch-all: Unboxable covers Int/Int8-64/Word/Word8-64/Char/Bool/Double/Float and reduces to 'False for everything else (https://hackage-content.haskell.org/package/dataframe-core-2.4.0.0/docs/DataFrame-Internal-Types.html); dimensional 1.6.2 (2026-01-01, https://hackage.haskell.org/package/dimensional) publishes no Data.Vector.Unboxed Unbox instances. A `Quantity DLength Double` column is therefore a BoxedColumn — Data.Vector.Vector of heap-allocated Quantity values, roughly 3x the memory of the equivalent Double column, and outside every unboxed kernel dataframe-core ships (Internal.AggKernelDirect, AggKernelPar, ParRadixSort, RadixRank, Hash). Worse, dataframe-core's schema layer has AssertRealColumn ('not a real-number type'), AllColumnsReal ('every column in the schema is a real (numeric), UNBOXED type') and AllDouble, which are exactly the constraints an ML/statistics path uses — so the api_sketch's headline program, in which `bill_len :: Quantity DLength Double` flows into `standardize @'["bill_len",...]` and `logisticClf`, does not typecheck against dataframe-learn without stripping units first. The flagship demo of the flagship feature is fiction.
### weaknesses
- THE HEADLINE CODE SKETCH DOES NOT COMPILE. `class HasCol n s a k | n s -> a k` with `instance {-# OVERLAPPING #-} HasCol n ('Fld n a k ': rest) a k` and `instance {-# OVERLAPPABLE #-} HasCol n rest a k => HasCol n (f ': rest) a k` is the classic fundeps-plus-overlap pattern that GHC rejects with 'Functional dependencies conflict between instance declarations' — the instance-consistency check is not waived by OVERLAPPING/OVERLAPPABLE (gitlab.haskell.org/ghc/ghc/-/issues/9210; haskell-cafe 2005-07 thread 'Overlapping Instances with Functional Dependencies'). Separately, `instance Unsatisfiable (...) => HasCol n '[] a k` violates the (even liberal) coverage condition: a and k appear nowhere in n or '[] and are not determined by the context. The standard fix — dispatch through `If (n == m)` into a helper class carrying a Bool index — works, but it is precisely 'type-family-only lookup' plus a fundep, which undercuts the next weakness.
- THE STATED TECHNICAL DIFFERENTIATOR OVER dataframe's EXISTING TYPED LAYER IS A TYPE-THEORY CLAIM THAT DOES NOT HOLD. The design says 'Fundeps, not type-family-only lookup, is the specific technical choice that keeps inference working — this is the concrete fix for Frames' annotation burden.' For a concrete schema, dataframe's closed family `Lookup n s` reduces immediately and determines the element type just as completely as a fundep does; no annotation is needed either way. For a polymorphic/skolem schema (generic pipeline code), NEITHER reduces — the fundep has no instance to fire on. There is no regime in which the fundep wins. Frames' annotation burden came from vinyl records, mandatory TH and rcast, not from lookup being a type family.
- THE ERASURE LAW CANNOT BE THE DRIFT DETECTOR IT IS CLAIMED TO BE. `erase (f x) == untypedF (erase x)` is claimed to 'turn dataframe API drift into a red test instead of a silent miscompile'. But D.Expr contains function fields (unaryFn, binaryFn, and CastWith's `Either String a1 -> a`), so it has no derivable Eq; the property can only be checked extensionally by evaluating both sides against generated frames. API drift is a compile error anyway (loud, free); what the property actually tests is null/NaN/empty-group semantics — which the risks section correctly identifies as the hard part and then relies on Hedgehog generators to cover.
- THE CI MATRIX IS UNSATISFIABLE ON DAY ZERO. M0 mandates {windows, ubuntu, macos} x GHC {9.10.3, 9.12.4, 9.14.1} from commit one, but dataframe's own CI is ubuntu-latest / ubuntu-24.04 only with ghc ['9.6.7','9.8.4','9.10.3','9.12.2'] (github.com/DataHaskell/dataframe .github/workflows/ci.yml and haskell-ci.yml), the package tested-with caps at 9.12.2, and Stackage has no 9.14 snapshot. From M2 onward one third of the matrix is red on a dependency Rowan does not maintain, on a platform its maintainer cannot reproduce. (The flip side is real: the Windows-CI gap is verified and is Rowan's single most defensible differentiator.)
- THE ERROR-MESSAGE BUDGET CONTRADICTS THE ERROR FORMAT ON EXACTLY THE TABLES THE PITCH TARGETS. The budget is '<=6 lines with the offending SYMBOL named in the first line'; the specified message renders `'Text "  Available: " ':<>: 'Text (RenderNames s0)`. On the 200-column production ETL table the design says it wants to serve, 'Available:' is a single line of ~2 KB. Truncating fixes the budget and removes the message's value. Type-level Levenshtein ('Nearest n s0') over 200 candidates is also a large constraint-solver workload on the error path, at the same time GHC is already being asked to normalise a 200-element type-level list.
- USER CODE IS HEAVY AND THE HAND-MAINTAINED SCHEMA IS THE WORST PART. The worked example spends ~25 lines on two hand-written schema aliases (Penguin, Clean) plus four `dropNull @"..."` calls plus a hand-written intermediate signature `Frame (Insert "ratio" Double 'Req Clean)` before it reaches three lines of pandas-equivalent work. Adding a column to the CSV means editing a type alias by hand, because the one mitigation — TH schema inference — is deliberately pushed off the required path for ideological reasons ('requiring TH is why Frames reads as an advanced Haskell tool'). That trade is backwards: TH-derived schemas are what make typed frames tolerable; hand-written type-level lists are what make them feel like an advanced Haskell tool. Meanwhile `Insert "ratio" Double 'Req Clean` and `Select ks s ++ AggSchema aggs` will appear in inferred types in GHCi, which is the design's own headline quickstart.
- THE FLAGSHIP GUARANTEE AND THE VERIFIED BUYER ARE DISJOINT. Phase/Role indices prevent fit-on-test and transform-before-fit — bugs that only bite someone who trains models repeatedly on tabular data in production. The design's own market section says that person does not exist in Haskell (Mercury: ~2M LOC, no DS/ML in its retrospective; Standard Chartered: trading infra, not DS) and names the sole verified buyer as 'the Haskell developer with an occasional data task', whose documented complaint is time-to-first-plot. For that user Rowan strictly ADDS concepts (DataKinds, a schema kind, OverloadedLabels, Phase, Role, Split, type applications) and compile time on top of a dataframe install that already reads CSV, plots to terminal and HTML, and fits a logistic regression. User #1 is not identified, and the value proposition points away from the only segment the design believes exists.
- THE EDA MISMATCH IS UNANSWERED, NOT SOLVED. mchav's rejection of type-level-first design rests on Hellerstein's point (quoted in the digest) that during exploration types are hypotheses revised continuously. Rowan's counter is a golden-error CI gate — which improves the legibility of failures but does nothing about the structural cost: in dataframe, revising your view of the data is a REPL expression; in Rowan it is a source edit to a type alias plus a recompile, every 30 seconds. The design concedes this only obliquely ('users may need Frame Clean annotations at pipeline boundaries').
- PERFORMANCE: THE DEFAULT PATH IS THE SLOW PATH BY POLICY, AND THE FAST PATH RELOCATES THE FRICTION IT CLAIMS TO ELIMINATE. rowan-learn inherits dataframe-learn's pure-Haskell numerics; rowan-tensor's default is a pure-Haskell fallback; BLAS lives in a separate package requiring a correct MSYS2 CLANG64 `pacman -S mingw-w64-clang-x86_64-openblas` plus a second `cabal install`. Shipping `matmul :: Shaped '[m,k] a -> Shaped '[k,n] a -> Shaped '[m,n] a` whose default implementation is a naive Haskell loop is a claim that will be benchmarked in public at M8. The design is honest that this is a trade; it is not honest that 'zero native dependencies' and 'competitive dense linear algebra' can both be the headline.
- SCHEDULE AND HEADCOUNT DO NOT RECONCILE. 13 packages, 36 weeks to 0.1, 16 months to 1.0, on 1-3 part-time devs — while the dependency shipped 1.0.0.0 -> 3.5.0.0 in five months, rewrote its typed schema representation once at 3.3.0.0, and Rowan's erasure targets a module literally named DataFrame.Internal.Expression (no stability contract). Budget realistically: M1+M2 are ten weeks of reimplementing existing code, and a nontrivial fraction of remaining capacity goes to chasing Internal-module churn.
- THE COLLABORATION POSTURE IS THE LEAST LIKELY VERSION OF ITSELF. 'rowan-schema proposed as a shared protocol that DataFrame.Typed could implement' asks the incumbent to reimplement a working, shipped, in-use type layer (consumed by eight DataFrame.Typed.* modules and by dataframe-learn) against a newcomer's incompatible kind encoding with zero users. The Tables.jl precedent is inverted: Tables.jl won because the protocol shipped BEFORE the implementations. Here the implementation shipped first, in the incumbent's package, and the protocol arrives second with no adopters. The stated fallback ('Rowan becomes a parallel effort') is the failure mode.
- GHC 10.0 RISK IS UNDERSTATED FOR THIS PARTICULAR DESIGN. Making Type and Constraint fully distinct is exactly the change that historically breaks type-family-and-fundep-heavy code, and Rowan is the most type-family-heavy design in the space. `default-language: GHC2021` handles the language-edition flip but nothing else, and there is no 10.0 alpha to test against.
### salvageable
- Phase- and Role-indexed estimators (`Split 'Train`, `Pipeline 'Fitted`) making fit-on-test and transform-before-fit type errors. This is the one guarantee no library in any language ships and it is small — offer it as a PR against dataframe-learn's existing DataFrame.ModelSelection rather than as a package.
- The golden type-error corpus as a CI gate: ~60 known-bad programs compiled via ghc as a subprocess, output normalized and byte-diffed against .golden files, with a hard budget (top-10 mistakes <=6 lines, offending symbol on line 1) and features cut when they miss it. This is a genuinely novel engineering practice for a typed Haskell library and it would pay off IMMEDIATELY on dataframe-core's existing DataFrame.Typed.Schema, whose assertion families (AssertAbsent, AssertKeyTypesMatch, AssertRealColumn, InnerJoinSchema) currently use plain TypeError.
- Upgrading dataframe-core's existing TypeError sites to GHC.TypeError.Unsatisfiable (base-4.19+/GHC 9.8+, GHC proposal #433) with hand-written messages including available column names and a 'did you mean'. Highest value-per-line item in the whole design, and it requires no new package.
- Windows CI for the dataframe monorepo. Verified absent: ci.yml is ubuntu-latest, haskell-ci.yml is ubuntu-24.04, both capped at GHC 9.12.2. Cheap, uncontroversial, immediately useful to the incumbent, and it establishes the contributor relationship the rest of the plan depends on.
- Inbound Arrow C Data Interface (ArrowSchema/ArrowArray import, release callback via ForeignPtr/bracket, structs copied in so there is no libarrow build dependency). Verified ecosystem gap — dataframe-arrow is export-only, harrow and hs-arrow are dead at 1 and 6 commits. Self-contained, high leverage, zero design risk.
- Schema-directed ingestion returning a column-level structured diff (expected type / inferred type / row number / raw offending text) instead of silent coercion — the direct fix for dataframe issue #177. Implement it against DataFrame.Typed.Schema's existing KnownSchema/schemaEvidence rather than a new schema kind.
- Hyperparameters-as-inspectable-data via Generic plus a free-category (not closure-chain) pipeline, so gridSearch/serialization/describe are generic over third-party estimators. Worth grafting onto dataframe-learn's monoid pipeline if its introspection is weaker.
- Runtime cpuid dispatch for C kernels instead of ox-arrays' -march=native, which bakes the build machine's ISA into a distributed artifact. Correct, and worth contributing wherever kernels land.
- Binding cblas.h/lapacke.h (the C headers OpenBLAS ships) rather than Fortran symbols or hmatrix's build system, with a CI-verified MSYS2 CLANG64 Windows lane. Genuinely unclaimed, and the Windows lane is the part nobody has had since 2017.
- Rule 0: the default install path has zero native dependencies, and every accelerated backend is a separate package rather than a cabal flag so the solver never considers it. Correct policy, correctly justified by the statistics -> dense-linear-algebra precedent.
- The deletability principle — every typed program has a mechanical de-typing to the untyped API, so users can bail out mid-pipeline. Worth preserving as a design constraint on any typed layer, including the incumbent's.
### rationale
This is the best-researched design of its kind I could attack, and it still fails on facts it could have checked. Its thesis rests on a gap that closed before the document was written: the typed schema layer it plans to spend weeks 2-10 building already ships inside its own hard dependencies. dataframe-core 2.4.0.0 exposes DataFrame.Typed.{Schema,Types,Record,Generic,Freeze,Util}, and DataFrame.Typed.Schema already contains Lookup/HasName, RemoveColumn/SubsetSchema/ExcludeSchema/RenameInSchema, AssertAbsent/AssertPresent/AssertDisjoint/AssertKeyTypesMatch, Inner/Left/Right/FullOuterJoinSchema, WrapMaybe/StripMaybeAt nullability, and KnownSchema with runtime reflection; dataframe-operations 2.4.0.0 exposes DataFrame.Typed.Expr with TExpr, col @"name", OverloadedLabels, and a fuller operator set (separate nullable-aware families) than Rowan's sketch, plus seven more Typed modules; dataframe-learn 2.4.1.0 exposes crossValidate, gridSearch and monoid pipelines that compile into expressions. So rowan-schema, rowan-frame, rowan-expr and most of rowan-pipeline are duplicates, and Rowan's incompatible schema kind (`[Field]` with a Nullability kind vs `[(Symbol,Type)]` with Maybe) means it cannot even consume the eight typed modules it duplicates — it is a competing typed API inside the incumbent's dependency cone, which is javelin's failure mode aimed at its own upstream. Three further load-bearing claims are refuted by inspection: (i) the reified-opcode rule buys zero optimizer visibility because the erasure target's Unary/Binary constructors carry UnUDF/BinUDF closures, so the Spark lesson is neither applied nor applicable; (ii) units are not free — Unboxable is a closed family with a `_ = 'False` catch-all and dimensional ships no Unbox instances, so Quantity columns are boxed and excluded from AllColumnsReal, which breaks the flagship worked example; (iii) the HasCol sketch does not compile (fundeps + OVERLAPPING triggers GHC's instance-consistency error; the Unsatisfiable instance violates coverage), and the fundep-beats-type-family inference argument that justifies diverging from the incumbent does not hold in either the concrete or the polymorphic regime.
