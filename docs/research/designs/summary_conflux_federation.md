# Conflux

## philosophy
Conflux is a federation layer, not an engine. Haskell's 2026 DS problem is not missing code — it is missing *contracts*. Verified inventory as of 2026-08-17: dataframe-core 2.4.0.0 and dataframe 3.5.0.0 (uploaded 2026-08-14, https://hackage.haskell.org/package/dataframe-core) give a columnar frame; dataframe-learn 2.4.1.0 already ships a scikit-learn-shaped `Fit`/`Predict` pair where "fit returns model metadata and predict compiles to a dataframe Expr" (https://hackage.haskell.org/package/dataframe-learn); dataframe-viz 1.3.1.0 gives terminal (granite) and Vega-Lite v5 backends (https://hackage.haskell.org/package/dataframe-viz); statistics 0.16.5.0, mwc-random 0.15.3.0, vector 0.13.2.0, massiv 1.0.5.0, orthotope 0.1.8.0, ox-arrays 0.2.0.1, horde-ad 0.3.0.0, ad 4.5.6, backprop 0.2.7.2, hasktorch 0.2.2.0, accelerate 1.4.0.0, chart-svg 0.8.3.2 all exist and all still build. What does not exist is any statement of how any two of them fit together. hmatrix's `Matrix`, massiv's `Array`, orthotope's `Ranked`, vector's `Vector`, dataframe's `Column`, hasktorch's `Tensor` are six incompatible universes with zero declared morphisms between them.

Three lessons from the research force this shape. (1) Every Haskell attempt that started by *rewriting the foundation* died: HLearn burned itself on SubHask and then blocked on dependent types; DataHaskell's 2017 promise of "a numeric library like NumPy and SciPy" never shipped; Owl (OCaml) reached technical excellence on 3,862 commits from one author and stalled anyway. (2) The artifacts that actually unified ecosystems were tiny specs, not big libraries — Julia's Tables.jl, ChainRulesCore, the Arrow C Data Interface (two frozen C structs), DLPack, and the Python Array API standard 2025.12, which explicitly abandoned NumPy's NEP 13/18 dispatch hooks in favour of "pass me a namespace" — a construct that is *literally a Haskell typeclass or record-of-functions*. (3) The failure mode that actually threatens Haskell DS right now is not a technical gap, it is fragmentation of ~110 interested people: javelin was competent and lost, and now pulls 19 downloads/month.

So Conflux writes almost no algorithms. It writes five contracts, ~a dozen thin adapters, one umbrella package, one documentation portal, one project template, and one notebook path — and it treats the *existing* maintainers as the project's primary stakeholders rather than its competition. The blessed dataframe is mchav's `DataFrame`, not a new one. The blessed estimator verb pair is dataframe-learn's `fit`/`predict`, generalized rather than replaced. The blessed array buffer is `Data.Vector.Storable.Vector`, because it is the only piece of the numeric stack with three maintainers and universal adoption. Success is measured in coherence, time-to-first-plot, and number of maintainers on the bench — not in lines of novel code. If in three years Conflux has been absorbed into DataHaskell and its contract packages are what everyone depends on, that is a win, not a defeat.

## scope
IN SCOPE FOR v1 (target: 1.0 with an explicit stable/unstable API split, copying Polars' 2024-07-01 precedent):

1. Five contract packages, each dependency-light, each versioned as a dated spec (`conflux-table-2027.03`-style spec revisions inside a semver package): a table protocol, an array/backend protocol, an estimator/hyperparameter protocol, an AD rule-registry protocol, and a plot-grammar protocol.
2. Adapters from those contracts onto: dataframe-core/-operations (blessed table), dataframe-learn (blessed estimators), dataframe-viz + chart-svg (plot renderers), statistics/mwc-random (stats + RNG), vector/massiv/orthotope (arrays), ad/backprop/horde-ad (AD rules). Optional, flag-gated, never on the default install path: hmatrix (BLAS), hasktorch (DL/GPU, non-Windows), duckdb-simple, accelerate, arrayfire.
3. Two interop structs implemented for real, because they are cheap and nobody has done the inbound half: Arrow C Data Interface *import* (dataframe-arrow 1.0.2.0 is export-only, Haskell→Python) and DLPack v1.3 import/export.
4. One batteries-included umbrella package `conflux` plus `Conflux.Prelude`, with a single documented quickstart that runs on Windows with **zero native dependencies**.
5. One documentation portal (diátaxis-structured: tutorial / how-to / reference / explanation), 6 end-to-end worked workflows, and a per-package "maintenance status + bus factor" badge — the thing the original DataHaskell inventory site failed to provide.
6. `conflux new` project templates (cabal + optional stack.yaml) and a pinned, prebuilt IHaskell kernel for Windows/Linux/macOS.
7. A written federation covenant and governance doc: named maintainers per package, a rule that Conflux never forks an upstream it can patch, and a standing offer of co-maintainership to upstream authors.
8. CI matrix: Windows-first. GHC 9.10.3 (Stackage LTS 24.55 floor), 9.12.4 (Stackage nightly, full HLS support, first GHC where `-fllvm` works with floating point on Windows — GHC #22487 breaks ≤9.10), 9.14.1 (GHC's first LTS, supported to ≥early 2028). `default-language: GHC2021` declared explicitly everywhere, because GHC 10.0 will silently default to GHC2024.

EXPLICITLY OUT OF SCOPE (v1 and probably forever):
- A new DataFrame. A new n-D array library. A new BLAS binding. A new CSV/Parquet reader. A new query optimizer. A new plotting engine. A new autodiff engine. A new streaming library. Every one of these already exists and every previous attempt to rebuild them killed its author's project.
- SIMD wrappers over GHC.Prim, `-march=native` C kernels, GPU kernels. Real gaps, wrong project — Conflux would inherit a research programme and a bus factor of one. Conflux instead defines the array backend seam so somebody else's SIMD backend can drop in.
- LinearTypes anywhere in a public signature (still "really unreliable" multiplicity polymorphism in the 9.14.1 user guide), `OverloadedRecordUpdate` (still flagged experimental with an explicit warning against long-lived libraries), and any dependence on Dependent Haskell (roadmap page updated 2026-08-14 declines to estimate Π/Σ types).
- ONNX via hs-onnxruntime-capi (AGPL-3.0-only, license-incompatible with MIT).
- WASM/JS browser targets (GHCup cross-bindists are Linux/Darwin-host only, capped at 9.12).
- Distributed computing. Leave distributed-process to DataHaskell's pillar 4.
- Any "curated library inventory" page. The original DataHaskell's main artifact was a list, and its named failure was "Choosing libraries ends up feeling like ordering from a diner." Conflux ships defaults, not menus.

## critique (score 3)
### fatal
- THE CENTRAL ADAPTER IS SPECIFIED AGAINST AN API THAT DOES NOT EXIST. The design states dataframe-learn 2.4.1.0 'already ships a scikit-learn-shaped Fit/Predict pair' and writes the adapter as `fit cfg df = Identity (Ridge (DFL.fit cfg df))`, calling it 'roughly 30 lines per model, zero reimplementation' and 'the single most important adapter in the project.' Verified against the actual haddock (https://hackage-content.haskell.org/package/dataframe-learn-2.4.1.0/docs/DataFrame-Model.html), upstream declares: `class Fit cfg input where { type ModelOf cfg input; type FrameReq cfg input :: FrameKind; fit :: cfg -> input -> FrameFor input -> FitResult (FrameFor input) (ModelOf cfg input) }` and `class Predict model where { type Prediction model; predict :: model -> Prediction model }`. Real `fit` takes THREE arguments — config, the target/feature `input`, and a `FrameFor input` — and returns a `FitResult` carrying a frame AND a model, not a bare model. `FrameFor` maps untyped `Expr`->`DataFrame` and typed `TExpr`->`TypedDataFrame`; `FitResult` returns `Fitted (cols :: [(Symbol,Type)]) model` for typed frames. Conflux's `class Estimator m where { type Config m; type Eff' m; fit :: Config m -> DataFrame -> Eff' m m }` has NO target argument, erases the FrameFor typed/untyped indexing, and discards FitResult's frame channel and schema tagging. The wrapper is strictly LESS expressive than the thing it wraps: it can only express the untyped path, deleting the compile-time schema tracking upstream already provides. Confirmed instance signature at DataFrame-LinearModel-Regression.html: `fit :: LinearConfig -> Expr Double -> FrameFor (Expr Double) -> FitResult (FrameFor (Expr Double)) (ModelOf LinearConfig (Expr Double))`.
- THE FLAGSHIP WORKED EXAMPLE DOES NOT TYPECHECK, AND THE PIPELINE CONSTRUCTOR IS UNCONSTRUCTIBLE. `data Step where Step :: (Estimator m, Predictor m) => Text -> Config m -> Step` existentially quantifies `m`, which appears only in constraints and under the NON-INJECTIVE associated family `Config m`. Given `L.step "model" (L.ridge L.defaults{L.alpha=1.0})`, GHC must solve `Config m ~ RidgeConfig` for an existential `m` — insoluble; every `step` call in the sample is an ambiguous-type error. Upstream avoided exactly this by indexing `Fit` on `cfg` (the thing the user writes) and deriving `ModelOf cfg input`; Conflux inverted the index and inherited the ambiguity. Three further breaks in the same 60-line sample: (a) `medianImputer`, `oneHotEncoder`, `standardScaler` are `Transformer`s but `Step` demands `(Estimator m, Predictor m)`; (b) `fitPipeline :: Pipeline -> DataFrame -> IO FittedPipeline` never receives the target column, which upstream's `fit` requires as its `input` argument, so it cannot fit anything — the label `"log_price"` is passed to gridSearch and then silently dropped; (c) `Right tuned <- pure (L.setStepParams bestParams spec)` is a partial pattern match in IO, in the tutorial, on the happy path. The single artifact meant to prove the API is tolerable is not compilable code.
- THE CLAIMED-NOVEL TUNING LAYER IS A STRINGLY-TYPED REGRESSION FROM AN ALREADY-GENERIC UPSTREAM. The design lists 'backend-generic Pipeline/crossValidate/gridSearch' as one of exactly three things that 'earn its existence' and 'today cannot span dataframe-learn and hasktorch.' Verified at DataFrame-ModelSelection.html, upstream already exports `gridSearch :: Int -> Int -> [c] -> (c -> DataFrame -> DataFrame -> Double) -> DataFrame -> GridSearchResult c` plus `crossValidate` and `crossValScore` — already fully polymorphic in the config type `c`, and type-safe because you enumerate real config records. Conflux replaces `[c]` with `ParamGrid` over `ParamMap = Map Text ParamValue` keyed by strings (`"model.alpha"`, `"scale.withMean"`) that fail at runtime via `ParamError`. A toolkit whose entire pitch is typed data work therefore ships a MORE dynamically-typed tuning API than the deliberately-untyped incumbent. This is precisely the 'looks more like an advanced Haskell tool than a data science tool' critique mchav levelled at Frames, inverted onto Conflux.
- THE 'BLAST-RADIUS FIREWALL' IS FALSE BY CONSTRUCTION — THE CONTRACTS ARE THE MOST CHURN-EXPOSED LAYER, NOT THE LEAST. The architecture claims adapters are the firewall so that 'when it breaks, exactly one Conflux package fails to build and the contract packages do not move.' But `conflux-estimator-api`'s public signatures use `Expr Double`, `DataFrame` and `ColumnName` (`predictExpr :: m -> Expr Double`, `transformExprs`, `fpExpr :: Expr Double`, `Metric`'s `DataFrame` argument), and `conflux-plot-api`'s `Channel` uses `Either ColumnName (Expr Double)` while `Plot` holds a `DataFrame`. These are dataframe-core types (verified: `Expr`, `DataFrame`, `Column` exported from `DataFrame.Core`, dataframe-core 2.4.0.0, uploaded 2026-08-14). The design's own package_breakdown omits dataframe-core from both packages' `builds_on`, and its stated rule is that a contract may depend only on base/text/containers/vector plus dataframe-core for the TABLE contract alone. Upstream went 1.0.0.0 (2026-03-22) -> 3.5.0.0 (2026-08-14) with 68 published versions and a typed-schema representation rewrite at 3.3.0.0. A dataframe-core 2.5 forces a major bump on all five 'contracts' — the artifacts the design says 'must outlive Conflux itself.' The architecture's core structural claim contradicts its own type signatures.
- EVERY CONTRACT ABSTRACTS OVER N=1 LIVE IMPLEMENTATION, WHICH INVERTS THE TABLES.JL / CHAINRULESCORE / NARWHALS PRECEDENT THE WHOLE DESIGN RESTS ON. Tables.jl unified DataFrames.jl + TypedTables.jl + CSV.jl + Query.jl + IndexedTables.jl; ChainRulesCore unified Zygote + ForwardDiff + Enzyme; narwhals spans pandas/Polars/PyArrow/DuckDB/PySpark/Dask/Ibis and was taken as a hard dependency by scikit-learn 1.9.0. Each was retrofitted onto MANY live implementations with real users. Haskell in 2026 has: one live dataframe (Frames' last release and last commit are both 2023-10-22, GHC <=9.4.6; javelin at 19 downloads/month), one live classical-ML package, one live plotting package that already emits both terminal and Vega-Lite from one `Chart` ADT, and AD packages with essentially no ML users. A protocol over one implementation is not federation, it is indirection. The design's own risk #2 concedes the point and sets the falsification test ('if by M6 no worked workflow genuinely needs two upstreams at once, the contracts are ceremony') — and the design cannot currently pass it, because the only second implementations it names are hasktorch (no Windows support, excluded from Conflux's flagship platform, ~38 Hackage downloads/30d) and hmatrix (flag-gated off, last release 2021-03-08).
- WINDOWS-FIRST — THE ONLY STATED DIFFERENTIATOR — IS STRUCTURALLY UNDELIVERABLE BECAUSE CONFLUX CONTROLS NONE OF THE CODE IT MUST KEEP GREEN. Verified: DataHaskell/dataframe's CI is Linux-only. `.github/workflows/ci.yml` is `runs-on: ubuntu-latest` with `ghc: ["9.6.7","9.8.4","9.10.3","9.12.2"]`; `haskell-ci.yml` is `runs-on: ubuntu-24.04` with ghc-9.4.8 through ghc-9.12.2. No windows-latest, no macOS, in either file. Conflux's zero-native-dependency umbrella depends on roughly nine upstream packages nobody tests on Windows (dataframe-core/-operations/-csv/-parquet/-parsing/-expr-serializer/-learn/-viz plus granite) and chart-svg. Conflux's own governance rule forbids forking ('never fork an upstream it can patch'), so every Windows break is blocked on one unpaid maintainer who has no Windows CI. Worse, upstream's tested ceiling is GHC 9.12.2 while Conflux mandates a 9.10.3/9.12.4/9.14.1 matrix — the 9.14.1 column is red on day one for reasons Conflux cannot fix. M1's gate, "'it builds on Windows' is the one claim Conflux must never break," is a promise made about somebody else's code, with the enforcement mechanism voluntarily surrendered.
### weaknesses
- THE BATTERIES-INCLUDED UMBRELLA SHIPS A SEVENTH ARRAY UNIVERSE, AN ALTERNATIVE NUMERIC PRELUDE, AND BOTH OPTICS LIBRARIES — CONTRADICTING ITS FOUNDING COMPLAINT. The philosophy opens by decrying 'six incompatible universes with zero declared morphisms between them.' Verified build-depends of chart-svg 0.8.3.2 (a default umbrella dependency): numhask (>=0.11 && <0.14), numhask-space, harpie (>=0.1 && <0.3), lens (>=5 && <5.4), optics-core (>=0.4 && <0.5), Color, cubicbezier, flatparse, formatn, markup-parse. harpie 0.2.0.0 (2026-01-10, Tony Day) is itself a rank-polymorphic multi-dimensional array library — a seventh universe, arriving transitively into the coherence project with no adapter written for it — alongside numhask, which replaces the standard numeric class hierarchy, and both major optics ecosystems at once.
- `conflux-plot-svg` IS NOT AN ADAPTER, IT IS A GRAMMAR-OF-GRAPHICS COMPILER, AND IT IS THE BIGGEST EFFORT UNDER-ESTIMATE IN THE PLAN. dataframe-viz 1.3.1.0 already exposes a `Chart` ADT with `toVegaSpec :: Chart -> Value` and ships BOTH terminal (granite) and web renderers from one spec — so 'one spec, N renderers' already exists upstream and `conflux-plot-api` largely re-declares it. The only genuinely new renderer is chart-svg, whose geometric model (numhask-space rectangles, harpie arrays, low-level SVG primitives) shares nothing with Vega-Lite's semantics. Rendering the same spec statically means implementing scale inference, stacking, facet layout, legend and axis tick algorithms, binning, density estimation and regression overlays — i.e. reimplementing what Vega-Lite is valuable FOR. M3 allots ~6 weeks for this plus two other renderers plus golden-file tests.
- `LinAlgBackend` HAS NO HONEST DEFAULT INSTANCE, AND THE ONLY WAY TO GIVE IT ONE IS THE FOUNDATION REWRITE THE SCOPE FORBIDS. The design declares `class ArrayBackend b => LinAlgBackend b` with `gemm`/`svd`/`solve`, puts 'a new BLAS binding' explicitly out of scope, flags hmatrix off by default, and makes `conflux-array-vector` (pure Haskell over Storable) the always-available default AND the 'correctness oracle for every other backend's property tests.' Either conflux-array-vector omits LinAlgBackend — in which case the class has zero instances in the default install and the design's own risk #7 ('close to a lie') is realized — or it implements SVD and a linear solver in pure Haskell, which is `dense-linear-algebra` 0.1.0.0 (2018, one release ever, characterized in the digest as 'naive algorithms, no decompositions worth the name') rebuilt, i.e. exactly the numeric-foundation work the scope section rules out.
- THE ANTI-LAMBDA RULE IS VIOLATED INSIDE THE FIRST CONTRACT THAT NEEDED IT. The design's hard architectural rule, offered as the defence against the Spark `Dataset[T]` trap it names in risk #8, is that 'every user-supplied computation crosses the boundary as a reified Expr, never a closure.' Yet `data Metric = Metric { metricName :: Text, metricFn :: ColumnName -> ColumnName -> DataFrame -> Double }` stores an opaque closure that no optimizer can see through and no serializer can encode, and `IsTable`'s methods and `Renderer`'s `render` are likewise closures. Metrics are the exact thing a tuning loop must inspect and serialize.
- USER-FACING ERGONOMICS READ AS AN ADVANCED-HASKELL ARTEFACT, WHICH IS THE REGISTER THE INCUMBENT'S DESIGN DOC EXPLICITLY REJECTED. Actual sample code: `col @Double "price" .> 0 .&&. col @Int "rooms" .>= 1`, `fromIntegral_ (col @Int "rooms")`, `log_`, `./`, `.-` — a type application per column reference plus a full shadow operator set plus trailing-underscore function variants, against Polars' `pl.col("price") > 0`. `L.defaults { L.alpha = 1.0 }` relies on the field selector monomorphising `Hyperparams p => defaults :: p`; with `alpha` present in ridge, lasso and elastic-net configs under DuplicateRecordFields it will not resolve. `cvReport.cvMean ! "rmse"` is a partial Map lookup on a string key never checked against the metric list that produced it. And the `@Double` annotations must agree with CSV type inference, which is already dataframe open issue #177 (silent Double->Int coercion).
- THE SUCCESS METRIC IS ARITHMETICALLY IMPLAUSIBLE. Risk #9 proposes '10 external (non-Conflux-maintainer) packages depending on conflux-table-api by M9' (~week 72). The incumbent has 4 Hackage reverse dependencies after 2.5 years, 1,267 commits, 68 releases and 261 stars — and 3 of those 4 are mchav's own, leaving one external consumer (symbolic-regression). Conflux targets more than 3x the incumbent's external adoption, within 18 months, for a layer that adds indirection rather than capability, in an ecosystem the design itself sizes at ~110 interested people.
- 25 PACKAGES OF GLUE, 9 MILESTONES, ~72 WEEKS, UNFUNDED, 1-3 DEVS — AND A GOVERNANCE RULE REQUIRING ~50 MAINTAINER SLOTS. GOVERNANCE.md mandates two named maintainers per package before any package reaches 1.0, while the DataHaskell survey the design cites found contributors want 'concrete, self-contained contributions like tutorials, docs, and bug fixes' and explicitly do NOT want maintainer roles. Glue packages have lower intrinsic contributor appeal than algorithms; the per-package fixed cost (cabal file, bounds, CI cell, Hackage release, changelog, docs, deprecation policy) is nearly constant regardless of how thin the package is.
- THE PROJECT'S NOVEL DELIVERABLES CAN BE ERASED BY THE INCUMBENT'S WEEKLY RELEASE CADENCE. conflux-duckdb exists only until dataframe-parquet's writer lands — which is already the funded, mentored GSoC 2026 project (issue #181, mentors mchav + adithyaov). Arrow ingestion is Phase 1 of DataHaskell's own published roadmap, so conflux-arrow's novelty has a maintainer with more hours and better access already pointed at it. The design's stated best outcome for its own flagship interop work is that upstream absorbs it — which means the successful version of this project is four patches, not 25 packages.
- GHC #22487 IS CITED AS THE JUSTIFICATION FOR THE RECOMMENDED COMPILER BUT IS IRRELEVANT TO THIS PROJECT, AND THE SPECIFIC CLAIM IS UNVERIFIED. The design pins 9.12.4 as recommended partly because it is 'the first GHC where -fllvm works with floating point on Windows.' Conflux ships no SIMD, no C kernels, no LLVM-dependent code, and none of its dependencies require -fllvm — the citation is decorative rigor. Separately, the best source I could reach (https://minoki.github.io/posts/2025-01-06-ghc-llvm-backend.html) confirms GHC <=9.10 is affected but does NOT confirm which version fixed it; gitlab.haskell.org/ghc/ghc/-/issues/22487 was behind an Anubis challenge and I could not verify the milestone. The 'first GHC where' claim is asserted beyond the evidence.
- 'ZERO NATIVE DEPENDENCIES' IS SOFTER THAN STATED AND UNTESTED ON THE TARGET PLATFORM. dataframe-parquet 1.5.0.0 depends on zstd and zlib. zstd 0.1.3.0 was uploaded 2021-09-27 and ships a default-on `standalone` flag meaning 'use a built-in copy of the zstd library' — so the promise is really 'no pacman step, but a bundled C build that must succeed under GHC's CLANG64 toolchain,' on a platform where the whole stack has no CI. snappy-hs 0.1.2.0 is genuinely pure Haskell, which helps, but a five-year-old bundled-C compression package is the kind of thing that breaks quietly on a new MSYS2 environment mid-migration (MINGW64 deprecated 2026-03-15).
- TYPE-LEVEL CONSTRUCT OF UNCERTAIN LEGALITY, WHICH I COULD NOT COMPILE-TEST. `class Monad (Eff b) => ArrayBackend b where { type Eff b :: Type -> Type; ... }` places a superclass constraint on the class's own associated type family. This is at minimum a fragile, non-idiomatic construct, and I believe GHC rejects superclass contexts that mention a family associated with the same class. I could not confirm — no GHC toolchain is installed on this machine (`which ghc cabal` returned nothing) — so I flag it as needing a five-minute compile check rather than asserting it as a defect. Given that the API sketch already contains one confirmed insoluble construct (the `Step` existential), the sketch as a whole should be assumed not to have been compiled.
- `Predictor` IS TYPED TO `Expr Double`, WHICH CANNOT EXPRESS THE CLASSIFIERS AND CLUSTERERS IT CLAIMS TO WRAP. `predictExpr :: m -> Expr Double` and `transformExprs :: m -> [(ColumnName, Expr Double)]`, yet the adapter is meant to cover logistic regression, SVM, decision trees, AdaBoost, k-means, GMM and DBSCAN — whose predictions are class labels (Text/Int) or cluster ids — while the `Metric` list includes `accuracy`, `f1` and `rocAuc`. Upstream handles this correctly with the associated type `Prediction model`; Conflux monomorphised it to Double and lost the ability to represent most of the model families in its own adapter table.
### salvageable
- INBOUND ARROW C DATA INTERFACE (import). Genuinely absent from Haskell and verified so: harrow has 1 commit, hs-arrow has 6 and is LGPL-2.1, Haskell is not in Arrow's official implementation list, and dataframe-arrow 1.0.2.0 is outbound-only ('Native-shared library exposing the dataframe lazy executor to Python via the Arrow C Data Interface') with ALL reported Hackage builds failing as of 2026-08-14. Frozen ABI, no libarrow build dependency, and producer/consumer ownership maps cleanly onto ForeignPtr + bracket. This is the single best idea in the document. It should be a pull request to dataframe-core, not the third layer of a federation.
- DLPACK v1.3 IMPORT/EXPORT. The tensor twin of the above: one frozen C struct, no GPU stack ownership required, buys zero-copy handoff to PyTorch/JAX/CuPy/NumPy. Same delivery advice — a small standalone package or an upstream PR, judged on its own merits rather than as a layer.
- HYPERPARAMETERS-AS-DATA VIA Generic. This is the one estimator-side gap I could verify as real: upstream's `gridSearch :: Int -> Int -> [c] -> (c -> DataFrame -> DataFrame -> Double) -> DataFrame -> GridSearchResult c` is already generic in `c` but has no way to enumerate, serialize or diff a config. A ~200-line Generic-derived `params`/`setParams`/`defaults` would make the EXISTING type-safe grid enumerable and serializable without replacing `[c]` with string maps. Ship it into dataframe-learn; keep the types, add the reflection.
- WINDOWS CI FOR THE DATAFRAME STACK. Verified missing (ci.yml is ubuntu-latest, haskell-ci.yml is ubuntu-24.04, no Windows or macOS runner). This is the highest value-per-hour item in the entire document, requires no new package, no new abstraction and no governance negotiation, and it is the only credible way to find out whether the Windows differentiator is even true before betting a project on it. Do this FIRST — it is also the cheapest possible falsification test of the whole Windows thesis.
- IHASKELL HACKAGE RELEASE CARRYING PR #1595's WINDOWS SUPPORT, PLUS PREBUILT KERNEL BUNDLES. The design identifies this correctly as the highest-leverage unblock in the onboarding chain (ihaskell-0.13.0.0, 2025-11-15, is bounded ghc <9.13 and predates the Windows work), and it is entirely upstream work requiring no Conflux package at all.
- THE GOVERNANCE INSTINCTS, DETACHED FROM THE PACKAGE PLAN. Two-maintainer minimum before 1.0; 'never fork what we can patch'; and above all the rule that every upstream interaction must arrive as a finished, tested PR closing an issue the maintainer already filed (massiv #146, dataframe #181/#152/#177/#191/#192). That last rule is the correct model for a 1-3 person effort in a ~110-person ecosystem, and it does not require a federation to execute.
- THE SCOPE DISCIPLINE THAT REFUSES THE FOUNDATION REWRITE. No new dataframe, no new n-D array library, no new BLAS binding, no new query optimizer, no LinearTypes in public signatures, no dependence on Dependent Haskell. This is the one classic Haskell-DS failure mode (HLearn/SubHask; DataHaskell's unshipped 2017 'NumPy and SciPy' plan) that the design genuinely avoids, and the discipline should carry to whatever replaces it.
- TIME-TO-FIRST-PLOT AS A CI-ENFORCED, BUILD-FAILING BUDGET. Cold-install wall clock, ghci-to-first-DataFrame, and time-to-first-plot measured on every run with a >20% regression failing the build. Julia's TTFX history justifies treating this as a P0 requirement rather than backlog, and it is a contribution any project can make to any package.
- DEPEND ON GRANULAR SUBPACKAGES WITH TIGHT BOUNDS, NEVER THE UMBRELLA. Correct given 68 published versions and 1.0.0.0 -> 3.5.0.0 in five months. Good advice for any downstream consumer regardless of whether Conflux exists.
### rationale
The diagnosis is largely right and the design deserves credit for dodging the one failure mode that killed HLearn and DataHaskell-2017: it refuses to rewrite the numeric foundation and refuses to bet on unshipped GHC features. But the prescription fails on verification at its two load-bearing points, and it repeats two OTHER failure modes the digest names explicitly.

VERIFICATION FAILURES. (1) The 'single most important adapter in the project' is written against an API that does not exist. Upstream `DataFrame.Model` declares `class Fit cfg input` with associated `ModelOf`/`FrameReq`/`FrameFor`/`FitResult` and `fit :: cfg -> input -> FrameFor input -> FitResult (FrameFor input) (ModelOf cfg input)` — three arguments, typed/untyped frame indexing, `Fitted (cols :: [(Symbol,Type)]) model` schema tagging. Conflux's two-argument `fit :: Config m -> DataFrame -> Eff' m m` has no target argument, erases the frame index, and is strictly less expressive than what it wraps. (2) The claimed-novel generic tuning already exists upstream and is already polymorphic in the config type (`gridSearch :: ... -> [c] -> (c -> DataFrame -> DataFrame -> Double) -> ...`); Conflux replaces type-safe `[c]` with string-keyed `Map Text ParamValue` that fails at runtime — a typed toolkit shipping a less-typed API than the deliberately-untyped incumbent. Meanwhile the flagship worked example does not typecheck: `Step :: (Estimator m, Predictor m) => Text -> Config m -> Step` is unconstructible over a non-injective `Config` family, three of its four pipeline steps are Transformers passed where Predictors are demanded, and `fitPipeline` never receives the target column.

REPEATED FAILURE MODES. The digest states the crosslang lesson outright: standardize the memory format at the bottom (Arrow) and the expression vocabulary at the top, 'but never in the middle' — the formally-designed `__dataframe__` interchange protocol died while the pragmatic narwhals shim won. Conflux's five contracts are precisely that middle layer, and the narwhals defence collapses because narwhals spans seven live backends with millions of users while every Conflux contract spans N=1 (Frames dead at GHC <=9.4.6; javelin at 19 downloads/month; hasktorch excluded from the flagship platform; hmatrix flagged off). And the digest's history lesson — 'DON'T build an inventory or a curation layer... its named failure was "Choosing libraries ends up feeling like ordering from a diner"' — is met by a project whose shipped artifacts are a curated umbrella, a documentation portal with per-package maintenance-status and bus-factor badges, and a set of flag-gated backend menus. That is DataHaskell v1's artifact with typeclasses attached.

STRUCTURAL. The 'blast-radius firewall' is contradicted by the design's own signatures: `Expr Double` and `DataFrame` appear in the public API of conflux-estimator-api and conflux-plot-api, so a dataframe-core 2.5 majors all five contracts, not one adapter. Windows-first — the only differentiator — is undeliverable: dataframe's CI is ubuntu-only across both workflow files with a tested ceiling of GHC 9.12.2, Conflux depends on ~9 such packages, mandates a 9.14.1 column, and forbids itself from forking. And the adoption target (10 external reverse deps by week 72) is over 3x the incumbent's total external adoption after 2.5 years and 1,267 commits.

WHO IS USER #1. Nobody. Segment (a) — the only verified buyer, Haskell devs with an occasional data task — installs `dataframe`, which is one package with a preloaded REPL, plots, Parquet and ML, and gets a worse deal from `conflux`: more packages, an extra indirection, a version-bound cliff at every upstream release, and a stringly-typed tuning API. Risk #2 concedes exactly this and then does not resolve it.

WHAT SURVIVES. Roughly four patches' worth of real value — inbound Arrow C Data Interface, DLPack, Generic hyperparameter reflection, and Windows CI for the dataframe stack — every one of which is better delivered as an upstream pull request than as a layer, and every one of which the design itself says it would prefer to hand upstream. A design whose own best outcome is its dissolution into four patches should be executed as four patches. 3/10: unusually well-researched, genuinely disciplined about the classic trap, and wrong about what it should build.
